**Сетевая модель в документах — выдержана:**
- кто чем управляет — таблица в `plan.md`; хост владеет выбором старта, уровнем, прочностью;
  каждая машина — своим экраном, файлом прогресса, часами секций;
- клиент меняет общее только `request_*` (`request_join`, `request_report_checkpoint`,
  `request_report_player_touch`), хост проверяет отправителя, правило логики
  (`can_reach`, `is_valid_start`, `CarryRules`) и допуск правдоподобия (T-36);
- события — надёжные RPC `authority` + `call_local`; полное состояние — `call_remote` новому
  пиру; синхронизатор только для положения, подвижный луч — детерминированно от часов секции
  без синхронизатора; пинг — `unreliable`, это правильно для замера;
- касание и чекпоинт судит машина без задержки (носильщик / владелец тела), последствие —
  хост по конфигу;
- смены хоста нет (T-28, `_apply_host_ended` + `SESSION_END_GRACE`), причина конца
  переживает перезагрузку `Main` в автозагрузке `Network` — новой автозагрузки нет;
- подключение: авторизация до `peer_connected` (третий не получает спавнов), полное
  состояние догоняет и вид (T-34), спавн второго — после выбора.

## Что хорошо

- Снимок чекпоинта сведён к «ID дальнего + пройдено», остальное выводится из сцены
  пересозданием `Content`. Формат не ломается при правке секций, сериализовать мир не нужно.
  Запись через `.tmp` с чистой `SaveFormat.pick` честно учитывает неатомарный rename на
  Windows.
- Сетевые решения обоснованы и проверяемы. Подвижный луч считается от часов секции без
  синхронизатора и согласован с «касание судит владелец». Пинг меряется на уровне игры, и
  объяснено, почему ENet RTT не видит `LagPeer`. API `MultiplayerPeerExtension` и
  авторизации проверены по справочнику 4.4.1, а не по памяти.
- «Задачи для трекера» мелкие и самостоятельно проверяемые, у каждой есть роль и тест
  готовности. Расхождения журнала F-001 закрыты решениями T-39…T-41 с порядком, при котором
  тесты не краснеют.
