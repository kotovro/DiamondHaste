# Команда агентов Diamond Heist — регламент

Этот файл читает каждый агент перед работой. Он задаёт роли, порядок работы над фичей,
артефакты и точки, где решает человек. Правила кода — `ARCHITECTURE.md`, системные
решения — `docs/tech/`, игра — `DESIGN.md`. Откуда взяты правила — `docs/agents/RESEARCH.md`
(агентам читать не нужно).

## Главная проблема, которую решает регламент

Агенты с разными компетенциями должны работать согласованно, не размывая единое видение
игры, а творческие решения должны оставаться за человеком. Поэтому:

1. **Каждая роль владеет одним видом артефакта** и не правит чужие. Связь между ролями —
   файлы по шаблонам, а не пересказ в чате.
2. **Решения — в документах, а не в памяти агента.** Что не записано в `DESIGN.md`,
   `docs/tech/` или артефактах фичи, то не решено.
3. **«Готово» доказывается запуском, а не словами.** Агент прикладывает команду и её итог.
4. **Запреты закреплены инструментами** (`.claude/settings.json`, CI, тесты), а не только
   просьбами в тексте.
5. **Человек решает всё творческое и всё необратимое.** Агенты предлагают варианты.

## Роли

| Роль | Файл агента | Владеет | Не трогает |
|---|---|---|---|
| Владелец (человек) | — | `DESIGN.md`, ответы на открытые вопросы, приоритеты, баланс в `data/*.tres`, ощущение от игры | — |
| Ведущий (основная сессия Claude) | `CLAUDE.md` + этот файл | Порядок работы, ветки, PR, `STATUS.md` фичи, вызов ролей | Код и документы ролей пишет не сам, если роль определена |
| Геймдизайнер-аналитик | `.claude/agents/game-designer.md` | `card.md` фичи, запросы решений `decision-*.md` | `DESIGN.md`, код, `docs/tech/` |
| Архитектор | `.claude/agents/architect.md` | `plan.md` фичи, `docs/tech/*`, журнал решений `docs/tech/00-index.md`, `project.godot` | `DESIGN.md`, реализация |
| Тест-инженер | `.claude/agents/test-engineer.md` | `tests/**`, `qa-manual.md` фичи | `scripts/**`, `scenes/**` (кроме тестовых сцен в `tests/`) |
| Программист | `.claude/agents/programmer.md` | `scripts/**`, `scenes/**` (кроме секций), `data/*.tres` новых конфигов, `locale/*` | `tests/**`, `docs/**`, `project.godot` |
| Ревьюер | `.claude/agents/reviewer.md` | `review.md` фичи | Всё остальное — только читает |
| Левел-дизайнер | `.claude/agents/level-designer.md` | `scenes/sections/**`, `scenes/level/**`, конфиги секций, расстановка источников атмосферы и зон реверберации | Логику и узлы препятствий, звуковые файлы |
| Звуковой дизайнер | `.claude/agents/sound-designer.md` | `audio/**`, звуковые компоненты и `*AudioConfig`, строки звука в `assets/LICENSES.md`, звуковые пункты `qa-manual.md` | Логику, сеть, сцены секций, раскладку шин без H2 |
| Ассет-конвейер | `.claude/agents/asset-pipeline.md` | `art/**`, `assets/**`, `assets.lock.json`, `assets/LICENSES.md`, черновик `docs/art/REFERENCES.md` | Код, сцены уровней |

Ведущий — это основная сессия: подагенты в Claude Code не вызывают друг друга, всю
передачу между ролями делает ведущий.

**Дизайн шире механик.** Каждая фича описывается не только тем, что игрок делает, но и
тем, что он видит и слышит в ответ: карточка содержит раздел «Обратная связь», план —
раздел «Звук». Левел-дизайн включает акустику помещений, звук — отдельная роль.

**Арт-директора-агента нет:** визуальный стиль не выбран (`DESIGN.md`, вопрос 7), и это
решение владельца. Агенты готовят материал для решения — `docs/art/REFERENCES.md`
(референсы, направления, что есть среди бесплатных ассетов), — но не выбирают.

**Лицензии ассетов** — `docs/art/ASSET_POLICY.md`: по умолчанию CC0, максимум — CC BY с
указанием автора; всё с иными условиями — только с решения владельца. Политику меняет
только владелец.

## Артефакты фичи

Каждая фича живёт в папке `docs/work/<ID>-<slug>/`. `<ID>` — номер задачи в трекере
YouGile (`DIA-N`); фичи до подключения трекера — `F-NNN`.

| Файл | Кто пишет | Шаблон | Зачем |
|---|---|---|---|
| `STATUS.md` | ведущий | `templates/status.md` | Где фича сейчас, кто следующий, ссылки на артефакты |
| `card.md` | геймдизайнер | `templates/card.md` | Что видит и делает игрок, критерии приёмки, связь с `DESIGN.md` |
| `decision-NN.md` | геймдизайнер или архитектор | `templates/decision.md` | Вопрос владельцу с вариантами. Пока не отвечен — работа по нему стоит |
| `plan.md` | архитектор | `templates/plan.md` | Слои, контракты (сигналы, RPC, поля конфигов), кто чем управляет по сети, файлы, список тестов |
| `qa-manual.md` | тест-инженер | `templates/qa-manual.md` | Что проверяет человек руками в двух окнах (`tools\run_local_coop.cmd`) |
| `review.md` | ревьюер | `templates/review.md` | Вердикт, замечания с адресатом |

Артефакты фичи коммитятся в её ветку вместе с кодом. После слияния папка остаётся как
история решений.

## Трекер задач (YouGile)

Каждая фича, доработка и найденный долг отражены в трекере: проект `DiamondHeist`
(префикс `DIA`), доска «Таски и фичи». Владелец не обязан заводить задачи сам — это
работа ролей.

| Кто | Что делает в трекере |
|---|---|
| Ведущий | Заводит задачу на H0 (или берёт задачу владельца) — её номер становится `<ID>`. Двигает её по колонкам: «Беклог» → «В работе» (начат шаг 1) → «Требует валидации» (PR влит в `dev`, ждём H3) → «Готово» (H3 пройдена, задача выполнена). В описание задачи — ссылки на папку фичи и PR. Единственный, кто пишет в трекер: остальные роли передают ему списки в своих артефактах |
| Геймдизайнер | Если задача владельца — это несколько фич, предлагает разбиение в разделе карточки «Декомпозиция» (что отдельно проверяется игроком) |
| Архитектор | В разделе плана «Задачи для трекера» раскладывает реализацию на подзадачи: каждая — самостоятельно проверяемая часть (слой, система, сцена), с ролью-исполнителем. Крупное — отдельной фичей со своим `DIA-N` |
| Ревьюер, все роли | Неблокирующие замечания и долг, которые не правятся в этой фиче, отмечают в своём артефакте пометкой «в трекер» |

Ведущий заводит подзадачи из «Декомпозиции» и «Задач для трекера» подзадачами задачи фичи,
закрывает каждую, когда её часть влита в ветку фичи, а пометки «в трекер» переносит в
«Беклог» отдельными задачами со ссылкой на источник. Задачи, предложенные агентами, — это
предложения: работа по ним начинается только после решения владельца (H0).

## Порядок работы над фичей

```
H0 владелец ставит задачу
 └─ 1. геймдизайнер → card.md (+ decision-*.md, если упёрся в открытый вопрос)
     └─ H1 владелец утверждает карточку / отвечает на decision
         └─ 2. архитектор → plan.md (+ правки docs/tech и журнала решений)
             └─ H2 владелец утверждает план, если он задевает список «H2» ниже
                 └─ 3. тест-инженер → тесты по plan.md (красные) + qa-manual.md
                     └─ 4. программист → код, пока run_tests не зелёный
                         └─ 4з. звуковой дизайнер → звуки на сигналы (если в плане есть раздел «Звук»)
                         └─ 5. ревьюер → review.md, сам перезапускает тесты
                             ├─ замечания → адресату (шаг 1–4), не дальше 2 кругов
                             └─ одобрено → ведущий: PR в dev с автослиянием
                                 └─ H3 владелец проходит qa-manual.md в двух окнах
```

Правила переходов:

- **Вход проверяется на входе.** Каждая роль сначала сверяет полученный артефакт с
  `DESIGN.md`, `ARCHITECTURE.md` и `docs/tech/`. Нашла противоречие или пробел — возвращает
  ведущему блокер с вопросом и не додумывает. Ошибка, пропущенная на шаге 1, дороже всего
  на шаге 4.
- **Тесты пишет не тот, кто пишет код.** Тест-инженер работает по `plan.md`, а не по
  реализации; программист не правит тесты. Если тест неверен — программист пишет об этом
  ведущему, тот передаёт тест-инженеру.
- **Цикл отладки ограничен.** На одну причину падения — до 3 попыток исправить. Потом
  программист останавливается и пишет диагноз: что падает, что пробовал, гипотеза.
- **Ревью — не больше 2 кругов.** На третьем ведущий поднимает вопрос владельцу.
- **Замечание всегда с адресатом:** `дизайнер` (пробел в карточке), `архитектор` (неверный
  контракт), `тесты` (неверный тест), `программист` (ошибка в коде), `владелец` (нужно
  решение). Ведущий отправляет замечание адресату, а не тому, кто ближе.
- **Мелкие правки** (опечатка, переименование, правка без изменения поведения) идут по
  короткому пути: программист → ревьюер. Карточка и план не нужны, но тесты зелёные.

## Где решает человек

**H0.** Задачу ставит только владелец. Агенты не заводят фичи сами, но могут предложить
список в отчёте.

**H1.** Карточка утверждается всегда. Особенно — если она касается открытых вопросов
`DESIGN.md` (несение, лазер, препятствия, взаимодействия, датчики, урон → управление),
реакции лазеров на алмаз, движущихся платформ, критериев интереса, языков.

**H2.** План утверждается, если он:
- вводит новый RPC или меняет, кто чем управляет по сети;
- меняет `project.godot` (автозагрузки, слои физики, действия ввода, настройки рендера);
- добавляет аддон, зависимость или автозагрузку;
- меняет решение из журнала `docs/tech/00-index.md` или формат сохранения;
- требует сменить модель несения или поведение сброса секции.

**H3.** Всё, что про ощущение, проверяет человек: управление, совместное несение под
задержкой 150 мс, ловля брошенного алмаза, читаемость поля зрения охраны, слышно ли
важное (повреждение алмаза, опасность, чекпоинт), ролики V-01.

**Стиль.** Визуальное и звуковое направление (`docs/art/REFERENCES.md`), любой ассет
уровня C и любое исключение из `docs/art/ASSET_POLICY.md` — решение владельца.
Слияние в `dev` по зелёным тестам этим не блокируется; фича закрывается и идёт в `main`
только после H3.

**Как агент спрашивает.** Через `decision-NN.md`: 2–3 варианта, для каждого — что
почувствует игрок, цена прототипа, риск для сети, что придётся переделать при смене
решения. Рекомендация — отдельной строкой и помеченная как рекомендация. Агент не выбирает
вариант за владельца и не вписывает ответ в `DESIGN.md`.

## Общие правила для всех ролей

**Контекст.** Читай только то, что нужно роли (список — в файле агента), карточку и план
своей фичи. Не загружай весь `docs/tech/` — открой файл, который описывает систему.

**Единый язык.** Термины — как в `DESIGN.md`: алмаз, секция, чекпоинт, несение, передача,
бросок, прочность, выносливость, носильщик, поимка, сброс секции. Не вводи синонимы.

**Доказательства.** Утверждение «тесты зелёные» сопровождается командой и последними
строками вывода (`VALIDATION OK` или список ошибок). Без этого шаг не считается сделанным.

**Отчёт ведущему** — в конце работы, не длиннее 15 строк:
```
Роль: <роль>   Фича: <ID>
Сделано: <1–3 строки>
Файлы: <список>
Проверка: <команда> → <итог>
Блокеры/вопросы: <нет | список с адресатом>
Дальше: <кому передать>
```

**Чего не делать никогда:**
- править `DESIGN.md`;
- менять числа баланса в существующих `data/*.tres` без задачи на это;
- отключать, пропускать или ослаблять тест, чтобы стало зелено;
- писать текст для игрока строкой — только ключ и `tr()`;
- `git push --force`, прямой пуш в `main` или `dev`, слияние без зелёных тестов.

## Правила работы с Godot 4.4.1 для агентов

- **Версия.** Проект на Godot 4.4.1. Возможности из 4.5+ недоступны (например,
  `@abstract` и функции с переменным числом аргументов). Перед использованием
  незнакомого метода сверься со справочником классов этой версии (путь — в `CLAUDE.md`),
  а не с памятью.
- **GdUnit4 5.1.1.** API смотреть в `addons/gdUnit4/src/`, а не по памяти: ветка 6.x
  отличается.
- **Файлы `.uid`.** Godot 4.4 создаёт `script.gd.uid` рядом с каждым скриптом. Новый
  скрипт → запустить `tools\run_tests.cmd` (там есть импорт), закоммитить `.uid` вместе со
  скриптом. При переносе — `git mv` обоих файлов. Значения `uid://…` не выдумывать: в
  `ext_resource` руками созданной сцены атрибут `uid` либо берётся из `.uid`-файла, либо
  опускается.
- **Сцены `.tscn` правятся текстом аккуратно:** небольшие изменения, `id` у
  `ext_resource`/`sub_resource` уникальны, формат не переписывается. После правки —
  `tools\run_tests.cmd` (тест `test_project_loads` ловит битые сцены).
- **Открытый редактор перезаписывает файлы.** Если владелец держит сцену открытой в
  редакторе, правка агента будет потеряна. Перед правкой `.tscn`/`.tres`/`project.godot`
  ведущий просит закрыть сцену или работать в отдельном worktree.
- **`project.godot`** меняет только архитектор и только после H2. Один писатель за раз.
- **Слои физики:** 1 `world`, 2 `players`, 3 `diamond`. Новые слои — через H2.
- **Логи.** `run_tests` считает провалом любые `SCRIPT ERROR` и `ERROR:` в выводе.
  `push_error` в штатной работе не используется.
- **Сеть без людей не проверить целиком.** Логика проверяется юнит-тестами, путь
  «запрос → событие» — интеграционными тестами на локальном пире (он же хост). Остальное
  (две машины, задержка) — в `qa-manual.md` для H3.

## Ветки и параллельная работа

- Ветка фичи: `feature/<ID>-<slug>` от `dev`. Слияние в `dev` — PR с автослиянием, только
  при зелёных тестах фичи и всех прежних (CI `tests.yml`).
- Параллельно работаем только над фичами, которые не трогают одни и те же сцены и
  `project.godot`. Каждая параллельная фича — в своём `git worktree` (у каждого worktree
  свой кэш `.godot/`, первый `run_tests` дольше из-за импорта).
- Внутри фичи роли идут последовательно. Исключение: ассет-конвейер и звуковой дизайнер
  могут подбирать и готовить файлы параллельно с программистом (по списку событий из
  плана); подключают их в сцены уже после программиста.

## Первая фича по регламенту: шаг 3 плана, совместное несение (A и B)

Пример, как роли делят эту задачу:

1. **Геймдизайнер** — карточка: что значит «несут двое» для игрока в моделях A (жёсткое
   крепление) и B (равновесие); наблюдаемые критерии для роликов V-01; что проверяет
   владелец. Вопрос 1 `DESIGN.md` остаётся открытым: цель — дать материал для решения.
2. **Архитектор** — контракт модели несения: набор методов стратегии (без общего
   базового класса, `ARCHITECTURE.md`, «Композиция»), поля конфигов A и B, кто что судит
   по сети, где имитируется задержка 150 мс.
3. **Тест-инженер** — общий контрактный тест, который гоняется по обеим реализациям,
   юнит-тесты на каждую модель, `qa-manual.md` для прогона в двух окнах с задержкой.
4. **Программист** — A, затем B, переключение моделью в конфиге.
5. **Левел-дизайнер** — тестовая трасса для роликов: прямая, поворот, узкий проход,
   ступени, разрыв для броска.
6. **Звуковой дизайнер** — заглушки на взятие вдвоём, потерю равновесия (для B) и удар
   алмаза: по роликам должно быть слышно, что происходит с грузом.
7. **H3** — владелец записывает ролики V-01 и решает вопрос 1.
