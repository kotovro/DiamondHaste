# Откуда взяты правила команды

Для людей. Агентам читать не нужно: правила уже в `TEAM.md` и файлах агентов.
Здесь — какая идея из какой работы взята и во что превратилась в Diamond Heist.

## Что берём

| Идея | Источник | Правило у нас |
|---|---|---|
| Рабочие процессы команды формализуются как SOP; роли передают друг другу структурированные документы, а не свободный диалог. Это гасит каскад ошибок между агентами | MetaGPT (Hong et al., ICLR 2024) | Порядок шагов в `TEAM.md`; артефакты по шаблонам `templates/` |
| Каждый агент владеет одним видом артефакта | Game-Creation-Agents (Zhou et al., 2026) | Таблица ролей: «Владеет / Не трогает» |
| Проверка идёт по собранной игре, а не по словам агентов; каждая проверка привязана к сборке | Game-Creation-Agents | «Готово» = вывод `run_tests`; ревьюер перезапускает тесты сам; в `review.md` и `qa-manual.md` записывается коммит |
| Ограничения обеспечивает управляющий слой, а не добрая воля агентов | Game-Creation-Agents (типизированный MCP-слой управления) | Запреты в `.claude/settings.json`, CI, тесты на содержимое |
| Найденная проблема уходит ответственному агенту | Game-Creation-Agents | Поле «Адресат» у каждого замечания |
| Ассеты делаются параллельно, сцены — последовательно, затем всё сводится в одну сборку | Game-Creation-Agents | Ассет-конвейер может идти параллельно с программистом; сцены и `project.godot` — один писатель |
| Агент-ассистент задаёт уточняющие вопросы, прежде чем отвечать («communicative dehallucination»); пары «инструктор — исполнитель»; фазы кодирования, ревью и тестирования | ChatDev (Qian et al., ACL 2024) | «Вход проверяется на входе»: при пробеле — блокер с вопросом, а не догадка; пара программист ↔ ревьюер с лимитом кругов |
| Агенты разных творческих ролей (нарратив, сцены, механики) обмениваются структурированными данными, чтобы сюжет, мир и игровой процесс не расходились | RPGAgent (Zhang et al., CHI 2026) | `card.md` → `plan.md` с таблицей опоры на `DESIGN.md`; единый язык терминов |
| RAG по документации движка уменьшает ошибки при работе с его инструментами; в генерацию кода закладываются паттерны и ограничения движка; автоматический прогон игры во время выполнения | AutoUE (Yin et al., Findings of ACL 2026) | Сверка API по справочнику классов Godot 4.4.1 и исходникам GdUnit4 5.1.1; раздел «Правила работы с Godot» в `TEAM.md`; интеграционные тесты со сценой |
| Агенты планирования, генерации, автоматизации и отладки; отладчик читает ошибки движка и исправляет | UniGen (Yang et al., 2025) | Цикл отладки программиста по выводу `run_tests` с лимитом 3 попытки на причину |
| Агенты исследуют варианты и предлагают их, а итоговое решение остаётся за дизайнером | Kruse, Connor, Marks (ACM TiiS, 2022) | Точки H0–H3; `decision.md` с 2–3 вариантами и отдельной рекомендацией |
| Главные проблемы мультиагентных систем: ограниченный контекст, распространение ошибок, стоимость, оценка результата, участие человека | He, Treude, Lo (TOSEM, 2025) | Каждая роль читает только свой список документов; отчёт ведущему ≤ 15 строк; агентов ровно столько, сколько видов артефактов |

## Что сознательно не берём

- **Полную автономию «от промпта до игры»** (Game-Creation-Agents, UniGen, AutoUE). Эти
  системы делают небольшие игры с нуля; у нас ручной уровень, открытые вопросы дизайна и
  сеть, где ощущение проверяет только человек.
- **Генерацию и поиск 3D-ассетов агентами** (AutoUE ищет по базе моделей). У нас ассеты
  идут через Blender по своему конвейеру, сторонние — с проверкой лицензии; стиль не выбран.
- **Свободный многоходовый диалог агентов** (ChatDev). Дорого по контексту и плохо
  проверяется; заменён артефактами.
- **Готовые механизмы интеграции с движком** из AutoUE (Unreal) и UniGen (Unity) —
  переносятся только идеи; GCA работает с Phaser.
